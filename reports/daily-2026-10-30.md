## 2. milind-soni/OpenMausBot

**8,015⭐ · 今日 +899 · TypeScript** · 创建于 2026-08-11 · [仓库](https://github.com/milind-soni/OpenMausBot)

**它到底是什么**：这是一个开源的 Grok Bot 替代品，本质上是一个基于 Electron 的桌面应用。它模拟了一个聊天界面，但里面的每一个“联系人”都是运行在你本地机器上的真实 AI 代理。你需要自己提供 Claude 或 Codex 的 CLI 工具，它负责管理这些代理的会话、记忆和工具调用。

**核心机制**：
- Bring Your Own Agent (BYO Agent)：不托管模型，而是通过配置本地 CLI 二进制文件（如 `claude`, `codex`）来驱动代理。
- 本地化架构：核心 Harness 服务器运行在 `127.0.0.1`，所有对话记录、密钥和事件存储在 `~/.openmausbot` 本地目录。
- 多代理编排：每个侧边栏的 Bot 都是独立的 Agent，拥有独立的性格、模型、虚拟机或云桌面环境。
- 工具集成：通过 Composio 连接 500+ 应用，允许 Agent 执行网页浏览、应用操作等“动手”任务。
- 跨平台桌面端：基于 React 和 Electron 构建，支持 macOS (Intel/Apple Silicon)、Windows 和 Ubuntu。

**使用场景**：
- 隐私敏感型用户：想要 Grok Bot 的多代理体验，但拒绝数据上传到 xAI 或 Meta 的云端。
- 开发者/极客：需要在一个界面统一管理多个不同的本地 AI 模型（Claude, Codex, Grok 等）。
- 自动化需求：需要具备“动手能力”的 Agent（如自动操作网页、调用 API），但希望执行环境可控。

**需要注意的坑**：
- 依赖本地 CLI：不能仅靠 API Key 使用，必须先在本地安装并配置 Claude、Codex 等官方 CLI 工具。
- 硬件资源消耗：运行多个 Agent 或其关联的云桌面/虚拟机需要较高的本地算力和内存。
- 平台兼容性限制：主机控制功能仅在 macOS 和 Ubuntu Xorg 下可用，Ubuntu Wayland 下被禁用。
- 上手门槛：相比简单的 API 封装，配置本地引擎和代理环境对新手来说有一定技术门槛。

## 4. CopilotKit/OpenBot

**8,490⭐ · 今日 +707 · TypeScript** · 创建于 2026-08-17 · [仓库](https://github.com/CopilotKit/OpenBot)

**它到底是什么**：这是一个运行在你自己基础设施上的开源 AI 代理协作平台。它通过 Docker 部署，模拟了一个多用户环境，让不同的 AI '同事'拥有独立的浏览器容器、文件系统和工具权限。它基于 AG-UI 协议接入任意框架（如 LangGraph）构建的代理，核心在于通过网关在执行任何操作前进行策略决策和审计记录，确保安全可控。

**核心机制**：
- AG-UI 协议：开放的标准协议，用于代理与用户之间的交互，解耦了代理与前端框架。
- 独立容器化环境：每个 Bot 拥有独立的 Chromium 浏览器实例和文件系统，互不干扰。
- 策略网关：所有对计算机、文件或 MCP 服务器的操作必须经过网关，网关负责决策是否允许执行并记录审计日志。
- Docker Compose 编排：使用 Docker Compose 启动整个栈，包括 PostgreSQL 数据库和各个 Bot 容器。
- CopilotKit Intelligence：后端服务，提供运行时密钥管理和状态追踪。
- 审计追踪：所有操作在执行前决策，执行后记录，确保可追溯性。

**使用场景**：
- 企业内部构建专属 AI 助手（如财务报销审核、会议纪要整理）。
- 需要完全控制 AI 行为、数据隐私和基础设施的团队。
- 测试和开发基于 AG-UI 协议的复杂 Agent 工作流。
- 不想依赖第三方托管服务，希望自建 AI 办公环境的公司。

**需要注意的坑**：
- 处于 Beta 阶段，存在边缘情况和潜在 Bug，稳定性有待验证。
- 资源消耗大：每个 Bot 都需要独立的浏览器容器，对硬件（内存/CPU）要求较高。
- 配置复杂：它是一个模板而非产品，需要自行配置 CopilotKit Intelligence、Docker、Bun 等环境。
- 需要技术能力：用户需要编写或配置 Agent 代码，不能直接开箱即用。

## 5. Renhuai123/ziwei-doushu

**10,826⭐ · 今日 +1146 · TypeScript** · 创建于 2026-05-01 · [仓库](https://github.com/Renhuai123/ziwei-doushu)

**它到底是什么**：这是一个基于 TypeScript 的紫微斗数开源排盘引擎，核心功能是利用倪海厦《天纪》体系算法计算命盘，并配套了包含 67.5 万张命盘和 13 维解读的 v4.0 数据集。用户可以通过命令行或代码调用引擎生成命盘，或直接读取数据集获取预生成的 13 个维度的详细解读文本。

**核心机制**：
- 确定性算法引擎: 使用 TypeScript 编写，包含农历公历转换、真太阳时校正、中国夏令时判定等核心逻辑。
- 13 维解读生成: 解读并非 AI 生成，而是基于规则库和命盘结构通过确定性算法生成的，保证同一输入恒得同一输出。
- 数据集格式: 采用 JSON Lines 格式存储，包含公历日期、时辰序号、性别、命宫主星及 13 个维度的 Markdown 解读文本。
- 古籍与原话库: 集成了《紫微斗数全书》原文（公有领域）和倪海厦《天纪》原话（特定许可），用于断语校正。
- 时区与经度校正: 支持通过经度差和均时差进行真太阳时校正，并支持海外出生地的 UTC 偏移。

**使用场景**：
- 开发者: 需要在 Web 或移动端应用中集成紫微斗数排盘功能的开发者。
- 命理研究者: 研究倪海厦体系或传统术数算法的学者。
- 商业产品: 需要合法商用排盘服务的公司（数据集为 CC BY 4.0）。
- 数据分析师: 分析 67 万张命盘数据以寻找规律。

**需要注意的坑**：
- 数据体积巨大: v4.0 数据集解压后达 56.6 GB，对存储和网络带宽要求高。
- 许可限制: 虽然数据集可商用，但引用的倪海厦原话属于 CC BY-NC-SA 4.0（禁止商用），使用时需注意区分。
- 六亲判断局限: 项目明确指出在六亲（父母兄弟子女）判断上存在局限，仅供参考。
- 技术门槛: 引擎包含 DST、真太阳时等复杂逻辑，集成难度高于简单排盘库。

- 工程化原则：实现计划强制要求测试驱动开发（TDD）、YAGNI（不写未来用不到的代码）和 DRY（不重复）。
