## 3. pbakaus/impeccable

**94,561⭐ · 今日 +2881 · Rust** · 创建于 2025-11-16 · [仓库](https://github.com/pbakaus/impeccable)

**它到底是什么**：这是一个为 AI 编码代理提供设计语言和规范的工具。它通过命令（如 `/impeccable polish`、`/impeccable critique`）引导 AI 生成更高质量、更符合品牌规范的代码，并内置 62 条确定性规则来检测“AI slop”（糟糕设计）。

**核心机制**：
- 设计上下文文件：通过 `/impeccable init` 读取项目代码生成 `PRODUCT.md`，后续所有命令基于此上下文执行。
- 确定性规则引擎：62 条硬编码规则（如过度使用 Inter 字体、拥挤的间距）用于检测设计问题，不依赖 LLM。
- 浏览器集成与渲染扫描：通过 Chrome 扩展或扫描本地开发服务器（Vite/Next.js 等）来获取渲染后的样式，检测对比度等视觉规则。
- 编辑器钩子：在 Claude Code、Cursor 等工具编辑代码时自动拦截并反馈设计问题，防止“AI slop”进入代码库。
- 24 个设计命令：分为 Steering（引导）、Review（审查）、Finish（打磨）、Iterate（迭代）等类别，直接控制 AI 的输出风格。

**使用场景**：
- AI 辅助开发：使用 Claude Code、Cursor 或 Copilot 开发前端项目时，确保生成的 UI 符合设计规范。
- 设计审查与审计：在 CI/CD 流程中运行 `npx impeccable detect`，自动检查可访问性、性能和主题一致性。
- 实时 UI 迭代：在浏览器中通过 Live 模式选中元素，快速生成并应用多个设计变体。
- 设计系统维护：通过 `document` 命令提取现有代码中的设计模式，固化到 `DESIGN.md` 中。

**需要注意的坑**：
- 依赖本地环境：检测对比度等视觉规则需要扫描本地开发服务器（如 localhost），无法直接扫描远程 URL。
- 配置成本：对于品牌字体或特定设计偏好，需要手动添加忽略规则或配置文件，否则会报错。
- 工具兼容性：虽然支持很多工具，但“编辑器钩子”功能需要工具支持，且安装后需手动重载工具才能生效。
- 规则局限性：规则基于静态分析，对于复杂的动态交互或非常规设计模式可能无法覆盖。

**核心机制**：

- Modelfile 集成：通过定义FROM和SYSTEM块，将提示词固化到本地模型文件中，实现模型行为的持久化修改。
- 配置优先级注入：针对特定平台（如Grok），将指令注入到配置槽位而非对话流中，以改变底层行为。

**使用场景**：
- 安全研究员和开发者测试模型的指令层级和提示词注入边界。

- 为本地部署的Ollama模型创建具有特定人设或能力的自定义版本。

**需要注意的坑**：
- 版本高度依赖：模型更新后，原本有效的提示词可能立即失效，需频繁维护。

- 维护成本高：由于模型更新频繁，需要持续验证和更新提示词库的有效性。

## 11. Donchitos/Claude-Code-Game-Studios

**28,765⭐ · 今日 +538 · Shell** · 创建于 2026-02-12 · [仓库](https://github.com/Donchitos/Claude-Code-Game-Studios)

**它到底是什么**：这是一个将 Claude Code 会话转化为完整游戏开发工作室的框架。它通过 49 个专业化 AI 代理和 74 个工作流技能，模拟真实游戏公司的层级结构（导演、部门主管、专员），强制执行设计文档、代码审查和 QA 流程，确保从概念到发布的全流程规范化。

**核心机制**：
- 多代理层级架构：将 49 个 AI 代理分为导演、部门主管和专员三层，模拟真实工作室分工。
- Claude Code 自定义配置：利用 `.claude` 目录下的 agents/skills/hooks/rules 文件结构，通过 Anthropic 的原生配置机制控制 AI 行为。
- 斜杠命令编排：提供 74 个 `/` 命令（如 `/dev-story`, `/code-review`）来驱动从设计、开发到 QA 的全生命周期。
- 引擎模板化：内置 Godot、Unity、Unreal Engine 的专用代理集（如 GDScript、GAS、UMG 专家）。
- 自动化钩子：15 个 Hooks 在提交、资产变更时自动触发验证和审计。
- Rigor 模式：通过 `modes.rigor` 控制文档生成量（从 1 页到 30+ 页），平衡开发速度与文档规范。

**使用场景**：
- 独立开发者：希望像拥有完整团队一样进行开发，避免代码混乱和缺乏设计文档。
- 小型游戏团队：需要标准化流程，确保美术、程序、策划各司其职。
- 复杂项目维护：需要通过严格的 QA 和代码审查来管理大型代码库。
- 游戏架构学习：通过观察代理如何生成架构文档和决策来学习工程化思维。

**需要注意的坑**：
- 配置复杂度高：49 个代理和 74 个技能的学习曲线陡峭，新手容易迷失在配置中。
- Token 成本高昂：特别是使用 Opus 模型作为导演时，大量代理并行工作会产生巨额费用。
- 维护负担：需要手动维护大量的规则和钩子，随着项目变大，同步更新容易滞后。
- 非游戏引擎：它只是管理工具，不提供渲染或物理引擎，用户仍需自己编写核心游戏逻辑。
